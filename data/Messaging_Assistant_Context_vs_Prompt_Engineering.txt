Context Engineering vs Prompt Engineering
This article defines both terms precisely and uses concrete examples from Denta to show where each one actually shows up in a working system, since the two are often used interchangeably.
1. Scene
What a model produces is always shaped by two things together: the wording of the instructions it's given, and the information actually available to it when it generates a response. Neither one alone decides the outcome, the best-worded instruction still fails if the model doesn't have the fact it needs, and the right fact still gets misused if the instruction around it is unclear.
Context engineering is the discipline of deciding what information a model has access to at the moment it generates a response, everything it can see and draw on before it starts producing an answer. This is a broader discipline than it sounds, since it includes several things that might otherwise look like separate concerns. It includes state and memory management, what a system remembers from earlier in a conversation and what it deliberately forgets or keeps separate. It includes the documents a RAG pipeline retrieves and hands to the model before generation begins. It includes which tools a model has available to call, and what those tools are described as doing. And it includes prompt engineering itself, the instructions given to the model are one piece of its context, not something separate from it.
Prompt engineering, by contrast, is the practice of crafting the wording of an instruction given to a model, choosing phrasing, structure, examples, and formatting so the model behaves the way it's meant to. It's a subset of context engineering, not a competing discipline, the prompt is one component that lives inside a model's context, alongside everything else context engineering assembles around it.
A context window is the total amount of text a model can actually see and process at once, measured in tokens, and it's the physical space context engineering has to work within. Everything context engineering assembles, retrieved documents, conversation history, tool descriptions, the system prompt itself has to actually fit inside this one shared space before the model ever generates anything. The context window trap assumes that a larger window solves the problem of giving a model the right information. It doesn't. A bigger window means more can technically fit, but stuffing it with irrelevant or poorly structured content dilutes the model's attention across everything in it, including the parts that actually matter, and can make its output worse rather than better, even though nothing was technically missing. This is precisely why context engineering exists as its own discipline rather than being solved by bigger windows alone; the job was never just fitting information in, it's deciding what earns a place in that limited space and what doesn't.
2. Problem
The problem worth naming directly is the distinction itself, and how easily it collapses. Prompt engineering and context engineering are often used as if they're the same thing, since in the end, everything the model sees arrives as text. But they solve different failures. A patient asking Denta what time slots are free tomorrow gets an answer shaped by two separate engineering decisions: the wording of the instructions guiding how the model should behave, and what information, today's date, the retrieved clinic hours, and the conversation so far, was actually assembled into its context before it ever started generating. Conflating the two makes it easy to reach for the wrong fix when a reply goes wrong, rewording an instruction when the real problem was a missing fact, or restructuring what data the model receives when the real problem was an ambiguous instruction.
3. Approach
Context engineering
Denta's clearest example of context engineering is retrieval itself, covered across the RAG and Chunking articles. Every FAQ answer depends on which chunks the retriever pulls back and hands to the model before generation even begins. The system prompt's wording stays fixed from one request to the next, but what actually fills its context placeholder changes on every single request, decided entirely by the retriever. This is context engineering operating at the largest scale in the project, deciding what the model gets to see, before any instruction about how to use it even matters.
State management is the second example, and it's the one the hallucination article documents in full. Denta keeps the booking conversation and the FAQ conversation in two separate session stores, rather than one shared history, specifically so a chain with no tools can never inherit context that implies an action it has no way to verify. That separation is a context engineering decision, not a prompt engineering one; it changes what a chain has access to, not how it's instructed to behave once it has it.
Tools are the third piece. Giving the booking agent access to check_available_slots and book_appointment is itself a context engineering decision, deciding what capabilities exist in the model's context for a given conversation, before any docstring wording comes into play at all.
The phone number injection from the Tool Calling article is a clean, small example of the same principle. The patient's phone number is never asked for and never extracted from a conversation; it's injected directly into the system prompt before the model ever sees the conversation.
system_with_phone = SYSTEM_PROMPT + f"\n\nClient's WhatsApp number: {phone}"
	No instructions told the model to be more careful with phone numbers. The fix was deciding the model should never have to produce that fact from language at all, it should already be sitting in its context, correct, before generation starts.
The system prompt itself also belongs to context engineering, at the level of deciding that a system prompt exists and what categories of information it needs to carry, such as business name, domain, phone number, and retrieved context. Deciding that those slots need to be there is a context engineering decision. How each one is actually worded is where prompt engineering begins.
Prompt engineering
The RAG system prompt is the clearest example of prompt engineering in the project, once the decision to have a system prompt at all is already made.
RAG_SYSTEM_PROMPT = f"""You are a helpful assistant for {BUSINESS_NAME}.
Use the following retrieved context to answer the customer's question.
If the answer is not in the context, use your general {BUSINESS_DOMAIN} knowledge
but make clear it is general information. For business-specific questions you cannot
answer, suggest they call {BUSINESS_PHONE}.
Do not add closing remarks or unsolicited advice.
"""
	Every instruction here is prompt engineering, how to handle a gap in retrieved context, what tone to use, what to do when the answer genuinely isn't available. None of it decides what the model actually has; it only decides how the model should behave once it has something.
Tool docstrings are the second example, and they matter because they're read by the model as part of the prompt on every turn, covered in the schema-as-prompt principle from the Tool Calling article.
@tool
def book_appointment(patient_name: str, phone: str, date: str, time: str, service: str) -> str:
    """
    Book an appointment and create a Google Calendar event.
 
    Only call this after:
    1. Confirming the client's preferred date and time using check_available_slots
    2. The client has explicitly confirmed their chosen slot
    3. You have collected: client name, phone number, date, time, and service type
 
    Do not guess any of these details — ask the client if any are missing.
    """
	

The tool's existence and the fact that the model has access to it is context engineering. The exact wording of when to call it, what order to follow, and what not to guess is prompt engineering, layered entirely on top of a capability that context engineering already decided should exist.
4. Results
Denta ran into one real failure in each category, and comparing them side by side shows how differently they present.
The context engineering failure was a chatbot that told a patient their appointment was confirmed, with the correct name, date, and time, when no booking had actually been made. Nothing about the wording of any instruction caused this. The actual cause was a state management decision; one conversation history was being shared across two different parts of the system instead of being kept separate. That shared history is what put a name, a date, and a time into the context of a system that had no tools and no way to check a calendar. State management is one of the pieces that make up context engineering, deciding what a system remembers and what it keeps siloed away from other parts of itself, and this is what a failure in that piece looks like: the wrong information ends up sitting in the wrong context window, available to a part of the system that was never meant to see it. The fix wasn't to reword an instruction; it was a state management fix, keeping that conversation history properly separated so it could never again leak into a context where it didn't belong. That's what makes this a context engineering failure, specifically, the problem was what information was present in the window, caused by how the state was being managed, not how any instruction was phrased.
The prompt engineering failure was smaller and easier to spot. A tool's instructions included an example date used to show the model the expected format, and that example happened to be over a year in the past by the time it mattered. Since a model reads an example as part of its instructions on every single use, a stale example risks nudging its output toward the wrong year when resolving something like "book me in for next Tuesday." Fixing it meant nothing more than updating the wording of the example. Nothing about what information the model had access to needed to change; the date example was simply worded in a way that could mislead.
Put side by side, one failure came from what the system had access to, the other from how an instruction was worded. The same kind of mistake, an unhelpful answer to a patient, can come from either direction, which is exactly why treating the two as interchangeable makes a real bug harder to diagnose.
5. Key Takeaway
Prompt engineering and context engineering solve different failures, and the fix for one rarely fixes the other. Prompt engineering changes how a model behaves, given what it has. Context engineering changes what it has to begin with. In a system with tools, retrieval, and session memory, most of the genuinely dangerous failures, a fabricated confirmation, a wrong date, a missing fact, live in what the model was given access to, not in how politely or clearly it was asked to behave. Getting the prompt's wording right is necessary, but it's the smaller half of the problem. Deciding what belongs in the model's context in the first place is where most of the real engineering work in a system like Denta actually happens.
