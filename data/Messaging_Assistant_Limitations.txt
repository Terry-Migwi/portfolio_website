Denta's Limitations: What I Would Change and Why
This article documents three real limitations in Denta as evidence of judgment.
Why This Article Exists
A working system and a well-engineered system are not the same thing. The messaging assistant is a working system. Whether it would still work as intended if it had to be maintained, scaled, or handed to someone else is a different question entirely, and answering it honestly is the actual point of this article. Being able to build a working RAG chatbot is one skill. Being able to look at that same system and say plainly where it falls short, and why, is a different one, and it's the one that actually matters once a system has to be maintained, scaled, or handed to someone else. This article covers three limitations I would flag myself before anyone else found them.
Limitation 1: RAG Is Arguably the Wrong Tool for a Single 6KB Document
Denta's entire FAQ knowledge base is one document, small enough to fit inside a system prompt directly, with room to spare. Retrieval-augmented generation exists to solve two problems, a document too large to fit in a model's context window, and a document that changes often enough that re-embedding beats redeploying a prompt. Neither is true here. The document is small, and it does not change on any meaningful schedule.
Given that, the honest question is whether Pinecone, embeddings, chunking, and a retrieval step earn their cost against the simpler alternative, pasting the whole document into the system prompt and skipping retrieval entirely. For a document this size, the simpler version would very likely perform just as well, with less infrastructure, less latency, and one fewer external dependency that can fail.
This limitation shows that RAG is not necessarily the right engineering choice for this exact problem. It would be the right choice if the clinic's documentation grows past what comfortably fits in a prompt, multiple documents, longer policies, and a larger service catalogue. At that point, the infrastructure already in place is a real advantage. At the current scale, it is a demonstration of capability more than a necessity.
Limitation 2: Cost and Latency Costs
The full reply pipeline stacks cost and latency on every message. A single reply from Denta can involve up to four separate LLM calls in sequence, intent classification, the handler itself (RAG or the booking agent, sometimes with its own multiple tool-calling turns), and two anomaly checks, groundedness and scope, both running in-line before the reply goes out. The concurrency article's own load test measured a median FAQ reply time of 6.4 seconds, a direct consequence of that stack.
The anomaly checks are the clearest example of a deliberate trade-off with a real cost attached. They exist because of a genuine, documented failure, a fabricated booking confirmation with no calendar write behind it, and they're proven to catch that exact failure. But running two extra classification calls on every single reply, including the overwhelming majority that are completely fine, roughly doubles the API cost of every conversation turn to guard against a failure that, by nature, should be rare.
Limitation 3: Session Storage Gaps
There are two separate issues here, detailed below.
Session storage has a concurrency bug. SessionManager stores every conversation in a plain Python dictionary, and that dictionary was never written with concurrent access in mind. This surfaced during the concurrency load test, when a test harness bug caused two simulated patients to collide on the same session ID. I did not fix it because it would only trigger in the case of the same phone number sending two messages in the same instant, which is rare but not impossible, and worth stating as a known gap.
Session Manager does not survive a restart. Every session lives in memory, inside one running process. If the system were to restart, be redeployed, or scaled to a second server instance, every active conversation, mid-booking or otherwise, would be lost. For a single-instance demo, this is an acceptable trade-off. However, in a real deployment serving a real clinic, a lost mid-booking conversation is a real patient inconvenienced. A production version of this system would need session state in something shared and persistent. Redis would be a good choice in this case, given that I have already used it for Celery.
What This Demonstrates
Denta was built to demonstrate a set of techniques clearly, tool calling, RAG, orchestration, anomaly detection, and concurrency. It was not built to be a production system a real dental clinic should actually run, as it has not been optimised for production.
These are documented here because they are true, and because knowing them is more valuable than not knowing them. Self-assessing exactly where a system would break under a different set of demands, more documents, more users, more scrutiny, is a valuable engineering skill.
