JWT Security: Gating a Search API Behind a Login
This article documents how I added JWT authentication to the semantic search pipeline, what JWT security is, why it matters for a deployed API, and how the full login flow works from database to frontend.
1. Scene
Every API that is publicly accessible on the internet is reachable by anyone with the URL. For a portfolio project deployed on Hugging Face Spaces, that means anyone who finds the link can query the search engine, consume Pinecone quota, burn Claude API credits, and generate costs without any limit. Without authentication, there is no way to control who uses the system or how much they use it.
JWT, which stands for JSON Web Token, is a standard for securing APIs by requiring users to prove their identity before accessing protected resources. A user logs in once with their credentials. The server verifies those credentials and issues a token. The user presents that token on every subsequent request. The server verifies the token and processes the request. No database lookup is needed after login because the token itself carries the proof of identity.
JWT authentication is used across a wide range of production systems: web applications that need to distinguish between logged-in and anonymous users, mobile applications that authenticate against a backend API, microservices that need to verify the identity of callers across service boundaries, and developer platforms that gate access to paid features behind verified accounts.
I added JWT authentication to this pipeline to demonstrate a production-relevant security pattern and to control access to the deployed Hugging Face Spaces demo. Anyone visiting the URL sees a login screen. Only users with valid credentials can reach the search interface.
2. Problem
A deployed search API with no authentication has two problems.
The first is cost exposure. This pipeline makes three external API calls per query: a HuggingFace embedding call, a Pinecone retrieval call, and a Claude generation call. Each has a cost in API spend and latency. An unauthenticated public endpoint means anyone can trigger those calls at any rate, with no limit and no accountability. A single automated script hitting the endpoint repeatedly could exhaust API quotas in minutes.
The second is access control. A portfolio demo is meant to be shown to specific people, such as potential employers, clients, or collaborators, not to the general public. Without authentication there is no way to distinguish between an invited reviewer and a random visitor. There is no way to revoke access, limit usage, or know who is using the system at all.
Session-based authentication, where the server stores a record of who is logged in, solves the access control problem but requires the server to maintain state. Every request has to hit the database to check whether the session is still valid. For a stateless API that may run across multiple instances, this adds complexity and a database dependency on every single request.
JWT solves both problems differently. The token is self-contained. After login, the server never touches the database to verify identity again. The token carries the user's email and an expiry timestamp, signed with a secret key only the server knows. Any attempt to modify the token invalidates the signature. The server can verify a token in memory in milliseconds, with no database call.
3. Approach
The implementation has four distinct layers: the users database, the authentication logic, the protected endpoints, and the frontend login screen.
Users database
User credentials are stored in a SQLite database with a single table containing four columns: an auto-incrementing ID, a unique email address, a hashed password, and a creation timestamp. The database is created automatically on first application startup, so there is no manual setup step needed on a fresh deployment.
Passwords are never stored as plain text. Every password is passed through two hashing steps before storage. The first is a SHA-256 pre-hash, which converts the password to a fixed 64-character hex string regardless of the original length. This step exists because bcrypt, the main hashing algorithm, has a hard limit of 72 bytes. A password longer than that gets silently truncated, which is a security issue. Pre-hashing with SHA-256 ensures every password arrives at bcrypt at a consistent, safe length. The second step is bcrypt itself, which applies a slow, computationally expensive hash designed specifically to resist brute-force attacks. The bcrypt hash is what gets stored in the database.
When a user logs in, the same two-step process is applied to the submitted password and the result is compared against the stored hash using passlib's verify() function. If they match, the login succeeds. The original password is never stored, logged, or compared directly.
New users are added by running a seed script directly against the database. For this project, the developer is the only user by default, so the seed script creates one account with a known email and password. When a visitor requests access, the developer adds their account using the same script, then shares the credentials directly. The script is run locally and never committed to the repository.
Authentication logic
Once login credentials are verified, the server issues a JWT. The token is constructed from three components. The header declares the signing algorithm, which in this case is HS256, a symmetric algorithm that uses the same secret key to sign and verify. The payload carries two fields: the user's email in a field called sub, short for subject, and an expiry timestamp computed by adding the configured token lifetime to the current time. The signature is generated by hashing the encoded header and payload together with a secret key stored in the environment variables.
The secret key is loaded from the environment. For local development it falls back to a randomly generated value if none is set. For Hugging Face Spaces it is set as a repository secret so the same key persists across restarts. A different key on every restart would invalidate all existing tokens immediately, forcing every user to log in again each time the Space restarts.
Token verification runs at the top of every protected endpoint. The incoming request must include an Authorization header with the token in the format Bearer followed by the token string. The verification function decodes the token using the same secret key, checks that the subject field is present, and confirms the token has not expired. If any of these checks fail, the function raises an HTTP 401 immediately and the endpoint handler never executes.
Protected endpoints
Both the /search and /rag endpoints are protected. The verification call sits at the very top of each handler, before the input guardrail and before any pipeline code. The order matters: a request with an invalid token should be rejected before any other processing happens, including the scope classification that runs the guardrail's own Claude call.
An except HTTPException: raise block in each handler ensures that the 401 raised by the token verification is not caught by the outer exception handler, which would convert it into a 500 and lose the authentication error entirely.
Frontend login screen
The frontend has two states: unauthenticated and authenticated. When the page loads, the search interface is hidden and a login form is displayed in its place. The login form collects an email address and a password and submits them to the /login endpoint. If the credentials are valid, the server returns a JWT and the frontend stores it in a JavaScript memory variable.
Storing the token in memory rather than in localStorage is a deliberate security decision. localStorage persists across sessions and is accessible to any JavaScript running on the page, including third-party scripts, making it a target for cross-site scripting attacks. A memory variable disappears when the tab closes, which limits the window of exposure. For a portfolio demo, this is the correct trade-off.
Once the token is stored, the login form is hidden and the search interface is revealed. Every subsequent call to /search or /rag includes the token in the Authorization header. If the server returns a 401 at any point, the frontend clears the token and returns the user to the login screen automatically.
A note at the bottom of the login form tells visitors that access is limited and directs them to contact the developer for credentials. When a visitor reaches out, the developer runs the seed script locally with the visitor's email and a temporary password, then shares those credentials directly. The visitor logs in, the frontend stores the token, and the search interface becomes accessible for that session.
4. Results

A visitor with valid credentials enters their email and password, the frontend calls /login, receives a token, and the search interface appears. Every query from that point runs against the fully authenticated pipeline with the token verified on each request.
Three scenarios confirm the authentication layer is working correctly. A request to /search with no token returns a 401 with the message "Invalid or expired token" and no pipeline cost is incurred. A request with a valid token proceeds through token verification, the input guardrail, hybrid search, re-ranking, and Claude generation, returning results normally. A request with an expired token returns a 401 and the frontend redirects the user to the login screen automatically.
5. Key Takeaway
JWT authentication solves the cost exposure and access control problems of a publicly deployed API without requiring the server to maintain session state. The token is issued once at login, verified in memory on every subsequent request, and carries its own expiry. The frontend login screen gates the user interface behind valid credentials, and the backend rejects unauthenticated requests before any pipeline cost is incurred. For a portfolio project on Hugging Face Spaces, this combination gives the developer full control over who can access the system while keeping the architecture stateless and the verification fast.
