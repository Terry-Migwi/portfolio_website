Deploying a Semantic Search Pipeline to Hugging Face Spaces with Docker
This article documents how I containerised and deployed the semantic search pipeline to Hugging Face Spaces, what Docker and Hugging Face Spaces are, why I chose them, and what deploying a pipeline of this complexity revealed about production containerisation.
1. Scene
The semantic search pipeline built across this series is a multi-component FastAPI application: hybrid search over a Pinecone vector index, cross-encoder re-ranking, JWT authentication, an input guardrail, and a Claude-powered RAG endpoint. Running it locally works well for development, but a pipeline that only runs on a developer's machine is not a portfolio project. It is a local experiment.
Deployment is what turns a local project into something a potential employer, client, or collaborator can actually use. It means the application runs on infrastructure that is accessible from anywhere, stays running without the developer's machine being on, and handles real requests from real users.
Docker is a containerisation tool that packages an application and all its dependencies into a single portable unit called a container. Instead of relying on the host machine having the right Python version, the right libraries, and the right environment variables configured correctly, a Docker container carries everything the application needs to run. The same container image runs identically on a developer's laptop, a cloud server, or a Hugging Face Space.
Hugging Face Spaces is a hosting platform for machine learning applications. It supports Docker deployments natively, runs containers on managed infrastructure, exposes applications on a public URL, and provides a secrets management system for API keys and credentials. For a portfolio project involving embedding models, vector databases, and LLM API calls, it is a natural deployment target. The platform is built for exactly this kind of application and is free to use at the scale of a portfolio demo.
2. Problem
A locally running application has three fundamental limitations for portfolio purposes.
The first is accessibility. A local server is only reachable from the machine it is running on. Sharing work with a potential employer or client requires either screen sharing, a recorded demo, or deploying to infrastructure they can reach directly. A live URL is significantly more compelling than a video.
The second is reproducibility. A local environment accumulates changes over time: library upgrades, configuration adjustments, files added and removed. What runs cleanly today may not run cleanly in three months when someone tries to set it up fresh. A Docker container freezes the environment at a known working state, making the application reproducible regardless of when or where it is run.
The third is credibility. A deployed application signals that the developer has taken the project through to completion. Building a pipeline is one skill. Deploying it, securing it, and making it accessible to others is a different and additional skill. A live deployment demonstrates both.
3. Approach
The deployment involved four distinct concerns: containerising the application with Docker, configuring the Hugging Face Space, managing secrets and credentials, and handling the persistence limitations of the deployment environment.
Docker containerisation
I wrote a Dockerfile that starts from a minimal Python 3.11 base image, creates a non-root user as required by Hugging Face Spaces, installs all dependencies from requirements.txt, caches the HuggingFace embedding model at build time, copies the application source, and starts the FastAPI server on port 7860.
I cached the embedding model at build time deliberately. The all-MiniLM-L6-v2 model is approximately 90MB. If it downloaded at runtime on every cold start, the first request after a Space restart would wait significantly longer while the model downloaded. Baking it into the image means the model is always available immediately when the container starts.
I pinned several packages in requirements.txt that required explicit attention. bcrypt is pinned to version 4.0.1 because newer versions are incompatible with passlib. I included pinecone-text for the BM25 sparse vector encoder, and python-jose and passlib for JWT authentication and password hashing respectively.
Hugging Face Spaces configuration
I configured the Space as a Docker Space through the README metadata block, which tells Hugging Face to use the Dockerfile rather than one of its standard framework templates. I connected the project to two Git remotes: one pointing to GitHub for version control and one pointing to the Hugging Face Space for deployment. Pushing to the Space remote triggers a rebuild and redeploy automatically.
Secrets and credentials
I stored the four external credentials the application needs, an Anthropic API key, a Pinecone API key, a JWT secret key, and a token expiry duration, as encrypted secrets in the Hugging Face Spaces settings. The application reads them at runtime via environment variables, so no credentials appear in the source code, the Git history, or the container image.
I generated the JWT secret key as a 64-character cryptographically random hex string and stored it as a persistent secret. Keeping it consistent across Space restarts matters: if the secret key changed on every restart, all existing tokens would be invalidated immediately, forcing every user to log in again after each deployment.
Filesystem and user persistence
Hugging Face Spaces free tier containers do not persist filesystem changes between restarts. Every time a Space restarts, the filesystem resets to the state of the Docker image. This has a direct implication for the users database: a SQLite database written to disk after the container starts is lost on the next restart.
I solved this by seeding the users table at application startup from environment secrets rather than relying on a file that persists between restarts. I stored two secrets, USER1_EMAIL and USER1_PASSWORD, in the Space settings. The startup event reads these values, creates the users table, and inserts the configured user on every boot. Adding a new user requires adding two new secrets and restarting the Space, with no code changes needed.
I included bm25_encoder.json directly in the repository. This file contains only term frequency data derived from the proposal documents and is not a secret. Including it in the repository ensures it is available inside the container without requiring a re-ingest step on every deployment.

5. Key Takeaway
Deploying a pipeline of this complexity revealed three things that local development does not surface.
The first is that containerised environments do not persist filesystem state between restarts. SQLite works correctly in local development where the database file survives server restarts. In a container on Hugging Face Spaces it does not. Any data that needs to survive restarts must come from the Docker image itself, from environment secrets injected at runtime, or from an external persistent store like a managed database. Designing for this constraint from the start is simpler than discovering it at deployment time.
The second is that dependency pinning matters more in a container than locally. A local conda environment accumulates specific versions over time through repeated installs. A container builds from scratch on every deployment, and unpinned dependencies may resolve to different versions than what was tested locally. Pinning bcrypt==4.0.1 explicitly ensured the password hashing behaviour matched what was tested, rather than breaking silently when a newer incompatible version was installed.
The third is that managing secrets is a concern because credentials embedded in source code, Git history, or Docker images can be exposed unintentionally and cannot be rotated without a rebuild. Storing them as environment secrets in Hugging Face Spaces means they are encrypted, never visible after being set, injected only at runtime, and can be rotated without rebuilding the image.
